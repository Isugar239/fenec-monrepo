# Лог: STM #1 OK, старая Pi мертва по SPI, STM #2 — подозрение на CS

Дата: 2026-06-28

Продолжение: [2026-06-26_spi_echo_firmware.md](2026-06-26_spi_echo_firmware.md), [2026-06-26_stm_original_bno_off.md](2026-06-26_stm_original_bno_off.md), [2026-06-25_spi_loopback.md](2026-06-25_spi_loopback.md), [2026-06-24_spi_debug.md](2026-06-24_spi_debug.md)

## Контекст

После серии сессий (24–26.06) оставались открытые вопросы: жив ли SPI на Pi, отвечают ли STM, почему MISO = 0xFF / нули. В этой сессии получены **решающие данные**: проблема старой малины подтверждена, первая STM по SPI работает, вторая жива по MCU, но на шине SPI по-прежнему `0xFF` — главный подозреваемый **CE/CS (chip select)**.

## Главные выводы сессии

| Компонент | Статус |
|-----------|--------|
| **Старая Raspberry Pi** | **Мертва по SPI** — на ней loopback и обмен не работали; гипотеза «Pi не шлёт» для старой платы **подтверждена** |
| **Новая Raspberry Pi** | **SPI OK** — замыкание MOSI↔MISO на Pi даёт побайтный loopback на CE0 и CE1 |
| **STM #1** (CE0, `/dev/spidev0.0`) | **Работает** — виден byte-echo по SPI (slave pipeline, сдвиг на 1 байт) |
| **STM #2** (CE1, `/dev/spidev0.1`) | **MCU жива** (мигание LED на PC5), но **SPI RX = все 0xFF** — MISO не драйвится при выборе CE1 |
| **Подозрение** | **CS/CE** — CE1 с Pi не доходит до PA4 (NSS) второй STM, или неверный CE mapping на кабеле |

## Хронология открытий

### 1. Старая Pi vs новая Pi

На **старой** Raspberry Pi SPI по сути не работал (нули в RX, обмен с STM бесполезен).

На **новой** Pi:
- Замкнуты MOSI↔MISO на header → `spi_loopback.py` / `spi_test` → **OK**, RX == TX (`0xA0..0xAF`)
- Оба chip-select (CE0, CE1) на новой Pi исправны

**Вывод:** для старой платы отпадает линия «чинить STM / прошивку» — корень был в Pi. Для новой платы Pi **не подозревается**.

### 2. Две STM подключены — разный ответ по CE

Запуск `spi_loopback_watch.py` (16 байт `0xA0..0xAF`, 1 МГц, CE0+CE1):

| CE | Устройство | Наблюдение | Интерпретация |
|----|------------|------------|---------------|
| CE0 | `/dev/spidev0.0` | `MISMATCH`, RX = `af a0 a1 a2 … ae` | **STM echo** — сдвиг pipeline: `RX[i] = TX[i−1]`, `RX[0]` = хвост прошлого кадра |
| CE1 | `/dev/spidev0.1` | `ALL_FF` | Slave **не драйвит MISO** — линия в high-Z, подтяжка вверх |

`spi_loopback_watch` помечает CE0 как `MISMATCH`, хотя связь есть: скрипт шлёт **16 байт** без warmup и ждёт `RX[0]==TX[0]` для тега `SLAVE_ECHO`.

### 3. `spidev_test` vs `tools` — ложное ощущение «всё OK»

Классический [SPI loopback test](https://importgeek.wordpress.com/2017/09/11/raspberry-pi-spi-loopback-testing/) (`spidev_test` с замкнутыми MOSI↔MISO) на **новой Pi проходит** — это проверка **только контроллера Pi**.

С **подключёнными STM** `spidev_test` на CE0 **не** даёт чистого loopback (частичное совпадение байт из-за ответа slave на MISO). Тесты в `tools` при этом **корректнее** отражают состояние шины Pi↔STM.

### 4. Подтверждение echo на CE0 (`spi_loopback.py`)

С учётом pipeline slave и одного preload-байта `0xA0` перед кадром:

```bash
sudo python3 tools/spi_loopback.py 0 0 1000000   # CE0 → FAIL без preload (RX[0]=0xAF)
# с preload 0xA0 перед xfer → echo_ok = True на CE0
```

| CE | TX | RX (типично) | Результат |
|----|-----|--------------|-----------|
| CE0 | `0xA0..0xB0` (17 байт) | `a0 a0 a1 … af` (после preload) | **STM #1 SPI echo OK** |
| CE1 | `0xA0..0xB0` (17 байт) | все `0xFF` | **FAIL** — MISO не драйвится |

### 5. Исследование STM #2 — MCU жива, SPI нет

Прошита тестовая прошивка **`tools/stm32duino_led_blink/stm32_led_blink_pc5.ino`**:
- мигание внешним LED на **PC5** (1 Гц + 3 быстрых вспышки при старте);
- тактирование **HSI only** (16 МГц) — тест «жива ли MCU» **без зависимости от внешнего кварца HSE**.

**Результат:** на **STM #2** LED **мигает** → микроконтроллер **загружается**, тактирование и GPIO работают.

При этом с Pi на CE1 по-прежнему **все `0xFF`** в `spi_loopback.py`.

**Вывод:** STM #2 **не «мёртвая»** в смысле MCU/кварца/питания. Проблема **узкая** — SPI slave не активируется при обмене через CE1. Наиболее вероятно: **CE (CS) не доходит до PA4 (NSS)** второй платы, или плата сидит не на том CE, который тестируем.

### 6. Отклонённые / пониженные гипотезы

| Гипотеза | Статус после сессии |
|----------|---------------------|
| SPI на Pi сломан | **Снята** для новой Pi (loopback OK) |
| Старая Pi исправна | **Отвергнута** |
| Обе STM молчат | **Снята** — STM #1 отвечает на CE0 |
| STM #2 не стартует (HSE/кварц) | **Понижена** — LED на PC5 мигает |
| MISO обрыв на обеих | **Частично** — CE0 MISO жив; для CE1 ещё не исключён обрыв MISO **вместе** с CS |
| **CE1 не доходит до PA4 STM #2** | **Главная гипотеза** |

## Схема подозрения (CE)

```
Pi CE0 (pin24, GPIO8) ──?──► STM #1 PA4 (NSS)  ✅ echo работает
Pi CE1 (pin26, GPIO7) ──?──► STM #2 PA4 (NSS)  ❌ 0xFF — CS не выбирает slave?
         SCK/MOSI/MISO общие на шине
```

Если CE1 не падает на PA4 второй STM, hardware NSS (`SSM=0`) не активирует SPI1 slave → MISO остаётся в Z → Pi читает `0xFF`. Это согласуется с осциллографом из лога 26.06 (CE0 на Pi есть, MISO молчит — там ещё не было разделения по платам).

## Следующие шаги

1. **Осциллограф, триггер на ↓CE1 (pin26):**
   - CE1 на Pi падает в 0?
   - **PA4 (NSS) на STM #2** падает синхронно с CE1?
   - SCK, MOSI на PA5/PA7 — есть?
   - PA6 (MISO) — драйвится или ровная 3.3 V?

2. **Перестановка плат на CE0/CE1** — если `0xFF` «переезжает» вместе с платой → проблема в STM/её разводке NSS; если остаётся на CE1 → обрыв CE1 в кабеле/разъёме.

3. **Проверить разводку кабеля** Pi ↔ control boards: какая физическая плата на CE0, какая на CE1 (ноги 0–1 vs 2–3).

4. После починки CE1: `sudo python3 tools/spi_loopback.py 0 1 1000000` → ожидать echo как на CE0; затем `spine_spi_test.py probe`.

5. Вернуть **оригинальную SPIneV1** на STM #1 (если стоит echo/LED тест) перед запуском робота.
