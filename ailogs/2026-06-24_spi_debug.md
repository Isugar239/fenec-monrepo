# Лог отладки: лапы Pupper V3 не работают (SPI / spine)

Дата: 2026-06-24

## Краткая суть проблемы
Лапы щенка не работают: моторы мягкие, момента нет.
- ROS2 / controller_manager / neural_controller — запускаются и активны.
- `effort` в ROS меняется (контроллер считает команды), но `/joint_states` (position) заморожены — обратной связи от суставов нет.
- BNO055 (IMU) сломан (`Remote I/O error`), но это НЕ причина отсутствия момента (код подставляет фиктивный IMU и продолжает).

Вывод по архитектуре: проблема НИЖЕ ROS — в обмене Pi <-> STM (spine) по SPI, либо STM <-> моторы (CAN).

## Архитектура связи (из кода)
- Pi мастер SPI, два устройства: `/dev/spidev0.0` (CE0/GPIO8, pin24) и `/dev/spidev0.1` (CE1/GPIO7, pin26).
- В `spi_send_receive` цикл по двум board:
  - board 0 -> `/dev/spidev0.0` -> leg_0 = 0 -> ноги 0–1
  - board 1 -> `/dev/spidev0.1` -> leg_0 = 2 -> ноги 2–3
- Пакет: 66 слов по 16 бит = 132 байта. MODE0, 8 бит/word, 6 MHz. На стороне Pi делается байт-своп каждого 16-бит слова.
- Контрольная сумма: XOR по 32 u32-словам (cmd) и 14 u32-словам (data), checksum в последнем слове.

## Распиновка STM (плата Nate711/Stanford)
- PA4 = NSS (= CE)
- PA5 = SCK
- PA6 = MISO
- PA7 = MOSI
- SPI1 slave.

## Пины Raspberry Pi (40-pin header)
- CE0 = GPIO8 (pin24) -> /dev/spidev0.0
- CE1 = GPIO7 (pin26) -> /dev/spidev0.1
- SCLK = GPIO11 (pin23)
- MOSI = GPIO10 (pin19)
- MISO = GPIO9 (pin21)

## Что сделали (изменения в коде)
1. `ros2_ws/src/control_board_hardware_interface/src/rt/rt_spi.cpp`
   - Добавлено логирование ошибок `ioctl(SPI_IOC_MESSAGE)` (раньше `(void)rv` игнорировал ошибки) + errno + счётчик неудач.
   - Счётчики ошибок SPI и плохих чексумм.
   - Периодическая печать первых слов TX/RX (каждые 100 итераций) и дамп RX при плохой чек-сумме.
2. `ros2_ws/src/control_board_hardware_interface/src/control_board_hardware_interface.cpp`
   - Детектор "замороженных" joint_states: считает подряд идущие read без изменений position, WARN каждые 50.
   - Периодическая печать `spi_data_->spi_driver_status` каждые 100 read.
3. Тестовые утилиты (в обход robot.service):
   - `tools/spi_test.c` + `tools/run_spi_test.sh` — одиночная SPI транзакция 132 байта, печать rv/errno и RX дампа.
   - `tools/spi_watch.c` + `tools/run_spi_watch.sh` — постоянный цикл, шлёт spine-совместимые пакеты на CE0 и CE1, проверяет checksum, ловит нулевые/замороженные ответы.
   - `tools/stm32duino_spi_slave/stm32_spi_slave.ino` — тестовая прошивка STM32F446 (STM32Duino, прямые регистры): SPI1 slave, счётчик принятых сообщений по UART (115200), теперь ещё и пишет паттерн в DR -> MISO.

## Результаты тестов
- `robot.service` логи: повторяющиеся WARN "No joint state updates detected ...", `SPI driver status: 0x03c30000`. Логи работают, проблема осталась.
- `spi_watch`: `rv=132` (ioctl проходит, ядро передаёт 132 байта), но `all_zero=1`, `rep_chk=0x00000000` -> в ответ MISO приходят нули. Pi шлёт такты, STM не отвечает.
- После замыкания MOSI<->MISO на `/dev/spidev0.1`: появились `0xFFFFFFFF` -> floats = -nan. Т.е. MISO читается как 0xFF (подтяжка вверх / линия занята / slave отдаёт 0xFF).
- Прошили тестовую прошивку STM32Duino на ПРАВУЮ STM (у левой сломан прошивочный разъём — можно шить только правую). Изменений нет, всё по нулям.
- Пользователь говорит: "сам SPI на малине работает".

## Главная гипотеза
Pi-сторона SPI работает (ioctl отдаёт байты), но реальных данных от STM нет. Наиболее вероятно:
- STM не слушает / не выставляет данные на MISO (NSS/CS не доходит до PA4, STM в reset/bootloader, или прошивка не обрабатывает SPI), ИЛИ
- неверный chip-select mapping (правая STM может сидеть на CE1, а не CE0), ИЛИ
- аппаратная проблема MISO (подтяжка/трансивер) — при замыкании видели 0xFF.

## Следующие шаги (когда вернёмся)
1. РЕШАЮЩИЙ ТЕСТ: loopback MOSI<->MISO при ПОЛНОСТЬЮ отключённой STM.
   - `sudo systemctl stop robot.service`
   - `cd ~/pupperv3-monorepo/tools && ./run_spi_test.sh /dev/spidev0.0 6000000`
   - Ожидание: RX повторяет TX (0xA0...). Если да -> SPI-контроллер Pi исправен; если нет -> проблема на Pi/шине/overlay.
2. Выяснить, на каком CE (CE0/GPIO8 или CE1/GPIO7) сидит ПРАВАЯ (прошитая) STM. Слать по очереди на оба и смотреть, какой ответит.
3. Осциллографом/логическим анализатором проверить:
   - дёргается ли CE (pin24/pin26) на время транзакции,
   - есть ли SCK на PA5, MOSI на PA7,
   - тянет ли STM MISO (PA6).
4. Проверить STM: BOOT0 = LOW (не в bootloader), сделать power-cycle, посмотреть UART (115200) тестовой прошивки -> растёт ли spi_count.
5. Проверить overlay на Pi: `dtparam=spi=on`, наличие `/dev/spidev0.0` и `/dev/spidev0.1`, `lsmod | rg spi`, `dmesg | rg -i spi`.
